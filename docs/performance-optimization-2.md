# Второй этап: обходы проекта и память FLP-событий

30 октября 2026. Продолжение [первого этапа](performance-optimization-1.md), исходный код приложения до изменений — `449940d`. Версия, релиз и сервер не менялись.

## Что изменилось

- `Analyze` получает FLP и аудио за один обход дерева. Список аудио заполняется на месте, без второго массива результатов. Снимок используется только внутри одной операции; каждый новый вызов заново читает папку.
- При поиске FLP относительные пути и `FileInfo` запрашиваются только для подходящих файлов. Исключения каталогов, автосохранений и служебных FLP сохранены.
- Выбор главного FLP и выбор FLP для метаданных читают только корень проекта. Раньше они обходили вложенные библиотеки сэмплов, а затем отбрасывали все вложенные FLP. Различия двух правил выбора сохранены: `MainFLP` предпочитает имя папки и исключает копии версий/конфликтов; помощник метаданных выбирает самый новый корневой FLP, включая такие копии.
- `Parse` сначала считает события существующим версионным обходчиком, затем один раз выделяет срез нужной ёмкости. Большие состояния плагинов пропускаются по длине; их содержимое не копируется. Дополнительный проход окупился в замерах всех четырёх размеров.

На Windows `DirEntry.Info()` уже использует сведения из списка каталога. Поэтому здесь основной выигрыш даёт устранение повторной рекурсии, а не отказ от самого вызова `Info()`. На Linux/Unix это также позволяет пропускать ненужные запросы сведений о файлах; отдельный коэффициент ускорения для Linux пока не измерен.

## Замеры Windows

Тот же i7-11800H, Windows/amd64, Go 1.22.12. Медианы трёх повторов по `500ms`. До/после использованы одинаковые генераторы данных. Это ориентиры одного компьютера, без статистической оценки всех реальных проектов.

Дерево проекта: 20 подпапок с однобайтовыми WAV, один сгенерированный FLP в корне. Полный `Analyze` измеряется с прогретым FLP-кэшем, чтобы отделить стоимость папок от поиска внутри состояний плагинов. Аудиофайлы не читаются целиком. Накопители, антивирус и файловый кэш влияют на время.

| Операция | До изменения | После | Изменение |
|---|---:|---:|---:|
| Полный анализ, 100 аудиофайлов | 5,53 мс | 2,66 мс | около 2,1× быстрее |
| Полный анализ, 5000 аудиофайлов | 40,23 мс | 20,81 мс | около 1,9× быстрее |
| Выделения памяти во втором сценарии | 7,85 МиБ | 4,46 МиБ | около 43% меньше |
| Число выделений во втором сценарии | около 56 000 | около 25 600 | около 54% меньше |
| Только список FLP, 5000 файлов | 15,43 мс | 12,69 мс | около 1,2× быстрее |
| Главный FLP, 100 файлов в подпапках | 2,19 мс | 0,180 мс | около 12× быстрее |
| Главный FLP, 5000 файлов в подпапках | 11,10 мс | 0,177 мс | около 63× быстрее |

Для двух строк `Главный FLP` исходный замер сделан **после** оптимизации перечисления FLP, но до отказа от рекурсии. Это отдельное сравнение двух вариантов выбора главного файла, а не измерение всей программы относительно исходного коммита. После изменения время этого выбора практически одинаково при 100 и 5000 файлах в подпапках; число записей в самом корне по-прежнему влияет на время.

Структурный разбор FLP, без `Info` и чтения с диска:

| Сценарий | Время до → после | Выделено до → после |
|---|---:|---:|
| Small: около 1000 событий, небольшие состояния | 21,9 → 11,2 мкс | 116,8 → 40,2 КиБ |
| Около 1000 событий, 1 МиБ состояний | 26,9 → 13,3 мкс | 116,8 → 40,2 КиБ |
| Около 1000 событий, 16 МиБ состояний | 13,1 → 9,24 мкс | 116,8 → 40,2 КиБ |
| 100 000 коротких событий | 4,21 → 0,852 мс | 16,94 → 3,05 МиБ |

Для 100 000 событий это около 4,9× по времени и 5,5× по суммарным выделениям; число выделений уменьшилось с 34 до 8. Разница между сценариями с большими состояниями не означает чтение всего блока: `Parse` оставляет ссылки на исходные байты и только проходит структуру событий. `B/op` — суммарные выделения, не пиковая RAM приложения.

## Корректность и проверки

Добавлены проверки совпадения списков с прежним обходом, порядка результатов, исключений папок, размеров файлов, приоритета `Audio/` перед `Samples/`, флагов `Used/Tracked/Included/Ignored`, ошибок повреждённых FLP и немедленного обновления после добавления, переименования и удаления. Отдельно проверяется выбор главного файла и кандидата для метаданных. Для отсутствующего проекта сохраняются пустые JSON-массивы.

Тест ссылок проверяет, что ссылка на папку не обходится рекурсивно, ссылка на FLP читается с размером целевого файла, а битая ссылка сохраняет ошибку. Если сам путь проекта является ссылкой, выбор главного FLP сохраняет поведение прежнего `WalkDir` и тоже не проходит по ней: перед `ReadDir` проверяется `Lstat`. Итоговый замер выше включает эту проверку. Локально Windows не разрешила создать symlink, поэтому этот тест был пропущен; он включён в CI и может выполняться там, где ОС разрешает создание ссылок.

Проверка парсера покрывает FL 11.4, 11.5, 24 и 26, включая особый размер события 172, все классы событий, большой блок плагина, точное совпадение байтов после повторной записи, отсутствие копирования payload, пустой и повреждённый поток и игнорируемые хвостовые байты.

Локально прошли `go vet ./...`, тесты `internal/flp` и `internal/ui`, выбранные Windows-тесты приложения, новые тесты проекта, существующие тесты названия FLP и подписывания рендеров, короткие запуски новых бенчмарков и сборка Windows. В Linux и Windows CI добавлен короткий запуск бенчмарков обходов, Windows CI также запускает тесты проекта. Полный Linux-набор выполняется в CI. Рабочие аккаунты, настройки, проекты и база сервера не использовались; изоляция `TestMain` сохранена. Ручных тестов интерфейса установленного приложения пока нет.

## Как повторить

`./scripts/benchmark.ps1 -Go ./dist/bench/tools/go/bin/go.exe -Bench '^BenchmarkProject(FLPs|Analyze|MainFLP)$' -Benchtime 500ms -Count 3 -OutputDirectory dist/bench/stage2-project`

Для парсера: тот же запуск с `-Bench '^BenchmarkFLP$/^(Small|Blob1MiB|Blob16MiB|Events100k)$/^Parse$'` и отдельным каталогом результатов. Исходные серии сохранены в `dist/bench/stage2-before-project`, `stage2-after-project`, `stage2-before-root`, `stage2-after-root-final`, `stage2-before-parse`, `stage2-after-parse`; внутри — `app.txt` либо `flp.txt` и параметры среды. Эти локальные артефакты не включаются в Git.

Результаты первого этапа относятся к поиску зависимостей внутри FLP, второго — к структуре событий и работе с деревом файлов. Их коэффициенты не нужно перемножать или называть ускорением всего приложения. Следующий шаг — замеры задержек пользовательских действий на изолированной установке перед решением о выпуске 0.10.0.
