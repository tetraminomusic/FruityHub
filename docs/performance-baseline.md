# Базовые замеры перед оптимизацией 0.10.0

Дата: 30 октября 2026. Код приложения: `a49d53e` (0.9.23), плюс бенчмарки из этого коммита. Версия приложения не менялась, релиз и развёртывание не выполнялись.

## Что измерялось

Windows/amd64, Intel Core i7-11800H, 16 логических процессоров, Go 1.22.12 (ветка Go из CI). Три повтора, `-benchtime=300ms`, обычная оптимизированная сборка тестов без race detector. В таблицах — медианы; это ориентиры на одном компьютере, без статистически подтверждённого сравнения двух реализаций. Долгая операция может занимать одну итерацию даже при `300ms`.

Все FLP, состояния плагинов и деревья файлов сгенерированы. Рабочие проекты, аккаунты, настройки и серверная база не использовались. Это профилирование функций исходного кода, а не замер интерфейса установленного приложения. Время запуска окна, WebView/GPU, настоящие библиотеки плагинов, Git/LFS, сеть и сервер под нагрузкой пока не измерены. Нельзя переносить полученные числа на любой реальный FLP или обещать ускорение всего приложения в несколько раз.

`Parse` читает структуру событий, оставляя ссылки на исходные блоки данных. `Info` дополнительно извлекает метаданные и ищет сэмплы внутри состояний плагинов. `ReadParseInfo` включает чтение временного файла; это повторные чтения с прогретым файловым кэшем ОС, не холодный диск. ZIP измеряется в памяти с подсчётом выходных байтов, без диска и сети. Обход папок использует настоящие временные файлы, но только однобайтовые.

МиБ здесь — 1 048 576 байт. `B/op` — суммарные выделения памяти за операцию, **не** пиковая RAM и не размер постоянно занятой памяти. `MB/s` у `Parse` нельзя интерпретировать как скорость чтения всего FLP: большие состояния плагинов он пропускает по длине.

ZIP одного файла 4 МиБ, включая создание и закрытие компрессора:

| Данные | Deflate BestSpeed | Zstd SpeedDefault | Выход/вход Deflate → Zstd |
|---|---:|---:|---:|
| Случайные байты | 6,46 мс | 3,33 мс | около 1 → 1 |
| Половина нули, половина случайные байты | 12,54 мс | 9,51 мс | 0,5155 → 0,5016 |
| Повторяющийся текст | 2,04 мс | 3,17 мс | 0,006159 → 0,0001483 |

Store занимает около 0,16 мс, но ничего не сжимает. Deflate выделяет около 1,16 МиБ на архив, Zstd — около 18,3–18,6 МиБ. На повторяющихся данных Zstd даёт гораздо меньший результат, но в этом сценарии работает медленнее. Это не подтверждает универсальное ускорение упаковки в 3–5 раз.

## CPU и память

Отдельный профиль `BenchmarkFLP/Blob1MiB/ParseInfo`, `3s`, один повтор: 174 мс/операцию. За весь процесс собрано 6,69 секунды CPU-сэмплов. Около **94,6% CPU** приходится на `regexp.FindAll`: `findPaths` — 75,0%, `unpackStreams` — 19,7% (в основном поиск base64). Эти значения вложенные, их нельзя складывать с общим процентом regexp. В профиле выделений около **89% alloc_space** приходится на `compress/flate.NewReader`, вызываемый через zlib при проверке потоков. Основное время уходит на поиск, основная масса выделений — на попытки распаковки.

Профили и исполняемый файл сохранены в `dist/bench/profile-flp-exact/`. Профилирование подтверждает приоритеты ниже, но не является профилем реальной пользовательской сессии.

## Приоритеты

1. **Поиск сэмплов внутри состояний плагинов.** В сценарии 1 МиБ `Info` дороже структурного разбора на несколько порядков. `audioRe` содержит широкий класс символов длиной до 400 перед расширением. Длинные печатные участки без расширений особенно дороги. Первый эксперимент: искать кандидаты по расширениям и проверять ограниченную область вокруг них; сохранять правила для регистра, разделителей, UTF-16 и границ пути. Сравнивать результаты поиска с текущей реализацией на отдельном корпусе, включая ложные совпадения и вложенное сжатие. Простая проверка наличия точки поможет только части входов и не заменит основной алгоритм.
2. **Распаковка и повторные проходы по состояниям.** В случайных данных встречаются сигнатуры zlib, вызывающие неудачные попытки распаковки и выделения памяти. `scanBlob` выполняет поиск в исходных и преобразованных данных, затем рекурсивно в распакованных потоках. Проверить стоимость ложных сигнатур, повторных одинаковых состояний, временных буферов и дедупликации найденных путей. Сохранить ограничения глубины и объёма распаковки. Принимать изменение по профилю и корректности, а не просто отключать поиск зависимостей.
3. **Много коротких FLP-событий.** Около 209 КБ файла со 100 000 событиями приводят к 17,8 МБ выделений при `Parse`: растёт срез `[]Event`. Проверить предварительную ёмкость, компактное хранение либо отдельный проход для чтения метаданных без построения всех событий. Возможный выигрыш прежде всего в памяти; не добавлять предварительный проход без сравнения времени.
4. **Повторные обходы дерева проекта.** `Project.FLPs` получает `FileInfo` даже для аудио и других файлов. `Analyze` затем снова обходит дерево; `MainFLP`, `ExtraFLPs` и другие методы тоже вызывают `FLPs`. Кандидат: единый снимок дерева на операцию и получение подробной информации только там, где она нужна. Число файлов здесь важнее объёма аудио; реальные диски, антивирус и сетевые папки нужно измерять отдельно.
5. **Упаковка.** Zstd уже используется, но лучший вариант зависит от данных. Проверить повторное использование компрессоров и размер выделений на один небольшой архив. Сжатые форматы уже отправляются с `Store`; убирать сжатие для остальных без оценки размера передачи нельзя.

## Go или Rust

Эти замеры не сравнивают Go с Rust. Сам по себе переход на другой язык не даёт обоснованного коэффициента ускорения. Сейчас наиболее обоснован первый эксперимент с алгоритмом поиска путей на Go: он занимает основное время в измеренном анализе больших состояний. После этого имеет смысл сравнить тот же поиск с отдельным прототипом Rust на **тех же байтах и с теми же найденными путями**, включая преобразования данных и стоимость границы языков. Полная миграция FLP-парсера пока не обоснована.

Порядок «профиль → устранение конкретного узкого места → повторный замер» соответствует [официальному руководству Go по pprof](https://go.dev/blog/pprof/). У Go regexp есть [гарантия линейного времени по длине входа](https://pkg.go.dev/regexp); высокая константа сложного выражения всё равно может делать полный проход дорогим. Здесь не выявлялась экспоненциальная сложность и не проводилось сравнение движков регулярных выражений.

## Как повторить

Из корня репозитория в PowerShell, с установленным Go:

```powershell
./scripts/benchmark.ps1
```

При отдельном Go, как в этом замере:

```powershell
./scripts/benchmark.ps1 -Go ./dist/bench/tools/go/bin/go.exe -OutputDirectory dist/bench/baseline
```

Скрипт изолирует HOME, USERPROFILE, APPDATA, LOCALAPPDATA и XDG_CONFIG_HOME; тесты `app` дополнительно используют существующий `TestMain`. Компилятор, зависимости, тестовые exe, временные настройки и результаты остаются в игнорируемом `dist/bench`. Вложенный `go.mod` исключает скачанные исходники инструментов из `go test ./...`. Скрипт не запускает установленный FruityHub и не сканирует системные каталоги плагинов.

Для профиля конкретной операции:

```powershell
./scripts/benchmark.ps1 -Go ./dist/bench/tools/go/bin/go.exe -Bench '^BenchmarkFLP$/^Blob1MiB$/^ParseInfo$' -Benchtime 3s -Count 1 -Profile -OutputDirectory dist/bench/profile-flp-exact
./dist/bench/tools/go/bin/go.exe tool pprof -top -cum dist/bench/profile-flp-exact/flp.test.exe dist/bench/profile-flp-exact/flp.cpu.pprof
./dist/bench/tools/go/bin/go.exe tool pprof -top -alloc_space dist/bench/profile-flp-exact/flp.test.exe dist/bench/profile-flp-exact/flp.mem.pprof
```

Исходные результаты полной серии: `dist/bench/baseline/flp.txt`, `app.txt`, параметры и исходный HEAD — `environment.txt`. Профили включают также подготовку фикстур: проверять стек нужной операции, не считать проценты всего процесса точной долей одного запроса. Для сравнения будущей оптимизации повторить серию с тем же Go, данными, числом процессоров и спокойной системой; увеличить длительность/число повторов и сравнить через benchstat. В Linux можно запускать `go test ./internal/flp ./internal/app -run '^$' -bench . -benchmem -count 3 -benchtime 300ms`; это отдельная платформа, её результаты не смешивать с Windows.

## План для 0.10.0

Локально прошли `go vet ./...`, тесты `internal/flp` и `internal/ui`, выбранные Windows-тесты `internal/app` из CI и `TestEmbeddedInCompressedState`, сборка `cmd/fruityhub`, UI-проверки Node, полная серия бенчмарков и короткие проверки бенчмарков для CI. Для Git и переименования временных файлов тестам потребовался запуск вне ограничений песочницы; изоляция `TestMain` сохранялась. Полный Linux-набор должен проверяться в CI; локальный WSL недоступен. Ручные тесты установленного приложения не проводились.

Сначала оптимизировать и проверить эквивалентность поиска зависимостей; затем повторить CPU/alloc-профили и замеры анализа, обходов и упаковки. Отдельно измерить задержку действий UI на изолированной установке с согласованным набором обезличенных проектов. Объявлять ускорение всего приложения только после замеров соответствующих пользовательских сценариев. Бенчмарки и этот отчёт не являются новым обновлением приложения.
