# Оптимизация вызовов Git при открытии проекта

30 октября 2026. Исходный код — `62f2903`. Продолжение [оптимизации загрузки интерфейса](performance-optimization-3.md). Версия приложения, релиз и развёртывание не менялись.

## Что показала трасса

`GIT_TRACE2_EVENT` зарегистрировал шесть запусков Git на первое получение `/api/project` для обычного репозитория с коммитом и `origin/main`:

1. `config --get uzbek.adopted`;
2. `remote get-url origin`;
3. `rev-parse --abbrev-ref HEAD`;
4. `status --porcelain=v1 -z --untracked-files=all`;
5. проверка существования `refs/remotes/origin/main`;
6. `rev-list --left-right --count HEAD...origin/main`.

Повторный запуск команды на Windows стоит заметного времени даже для маленького репозитория. В предыдущих этапах этот случай не измерялся: там использовались папки без `.git`.

## Что изменилось

- Ветка и изменения индекса/рабочего дерева читаются одним `status --porcelain=v2 --branch --no-ahead-behind -z --untracked-files=all`. NUL-разделители сохраняют имена с пробелами, Unicode и управляющими символами. Формат полей описан в [официальной документации git-status](https://git-scm.com/docs/git-status#_porcelain_format_version_2).
- Счётчики вычисляются отдельным `rev-list` относительно **полного ref `refs/remotes/origin/<ветка>`**. Используется OID HEAD из полученного статуса, чтобы переключение HEAD между командами не подменяло исходный коммит. Настроенный upstream может указывать на другой remote — приложение продолжает сравнивать с origin.
- Успешный `rev-list` больше не предваряется отдельной проверкой существования ref. При ошибке/пустом репозитории существование ref проверяется для сохранения прежних значений `-1/0` либо `0/0`.
- Чтение `uzbek.adopted` использует существующий короткий кэш Git-чтений: не более секунды, с проверкой изменений `.git/config`, HEAD и packed-refs. Для linked worktree с `.git`-файлом и объектов Git с дополнительным `Env` это новое кэширование отключено.
- Новый путь используется ответом экрана проекта и фоновым подсчётом уведомлений. При ошибке команды или неизвестном формате остаётся прежний путь чтения. Публичный `Status()` для других операций сохранён.

Список изменений, текущая ветка в новом снимке и счётчики **не кэшируются**. Файлы и refs перечитываются при каждом таком запросе. Команды fetch/push, автор пользовательских коммитов и настройки remotes не изменены. Сетевых запросов оптимизация не добавляет.

После изменений трасса первого ответа показывает **четыре запуска**, немедленного повторного — **два** (`status` и `rev-list`). Это число для корректного репозитория с существующей веткой origin; ошибки, отсутствие ветки и истечение короткого кэша могут потребовать дополнительных запусков.

## Замеры Windows

Windows/amd64, i7-11800H, Go 1.22.12, Git 2.51.1.windows.1. Три повтора по `500ms`, медианы. Синтетический репозиторий: один коммит, сгенерированный FLP с 1 МиБ состояния, локально созданный ref origin/main; URL remote — `example.invalid`, fetch не выполняется. Полный обработчик `/api/project` измеряется через `httptest`, без TCP и отрисовки браузера.

| Сценарий | До | После | Результат |
|---|---:|---:|---:|
| Повторное открытие с прогретыми короткими Git-чтениями | 244,7 мс | 131,0 мс | около 1,9× быстрее |
| Открытие с очищенным кэшем коротких Git-чтений | 350,6 мс | 254,5 мс | около 1,4× быстрее |

FLP-кэш и файловый кэш ОС предварительно прогреты в обоих случаях. Очистка короткого кэша входит в замер второго сценария. Число итераций невелико из-за стоимости запуска процессов; это ориентиры одного компьютера, не статистическая оценка всех проектов. Накопитель, защитное ПО, размер индекса и история репозитория могут менять результаты. Нельзя переносить эти коэффициенты на сетевую синхронизацию или время от клика до кадра.

Локальные исходные результаты: `dist/bench/git-before/app.txt` и `dist/bench/git-after/app.txt`; параметры среды — рядом. Они не включаются в Git. Повторение: `./scripts/benchmark.ps1 -Go ./dist/bench/tools/go/bin/go.exe -Bench '^BenchmarkGitProjectOpening$' -Benchtime 500ms -Count 3 -OutputDirectory dist/bench/git-after`. Git создаёт временные `.git`/worktree, поэтому ограниченная Windows-песочница может потребовать разрешённого запуска тестов вне её; `TestMain` сохраняет изоляцию настроек.

## Проверки

Новый снимок сравнивается с прежними `Status`, `Branch`, `AheadBehind` на чистом и изменённом дереве: staged/unstaged, удаление, переименование, Unicode, внутренние файлы, пустой репозиторий, ahead/diverged, смена ветки без ожидания, detached HEAD, другой upstream, удалённая ветка origin, конфликты, linked worktree, изменённые и неотслеживаемые файлы подмодуля. Отдельно проверяются NUL-имена и повреждённые записи, изменение adoption-настройки вне приложения и общая конфигурация worktree. Локальная ветка `origin/main` не считается существованием удалённой ветки origin/main.

Тест трассы также проверяет ответ API и отсутствие старых запросов ветки/статуса на обычном репозитории. Фоновые уведомления проверяются после создания/удаления файла и внешнего коммита, включая исключение служебных файлов из числа изменений. В Linux и Windows CI добавлен короткий запуск бенчмарка Git; Windows CI выполняет Git-тесты. Локально прошли Git-проверки, регрессии предыдущих этапов, `go vet` и сборка Windows. Полный Linux-набор проверяется в CI.

Репозитории, подмодули, коммиты, настройки и трассы тестов временные; живые проекты, аккаунты и серверная база не используются. Визуальный прогон браузера в этом этапе не выполнялся: измерен серверный ответ интерфейса. Ограничение визуальной проверки третьего этапа остаётся в соответствующем отчёте.
