# Третий этап: загрузка данных интерфейса

30 октября 2026. Исходный код до изменений — `0768131`. Версия приложения и сервер не менялись. Выполнены замеры и оптимизация API, используемого списком и экраном проекта. Визуальную часть этапа завершить не удалось: ограничение инструмента описано ниже.

## Найденное узкое место

Для артиста, темпа и длительности использовался тот же разбор FLP, который ищет все сэмплы внутри состояний плагинов. Поэтому первое дополнение списка метаданными могло выполнять полный поиск зависимостей для каждого проекта. Кроме того, `FLCompat` заново читал FLP с диска даже при уже заполненном кэше, чтобы получить только версию FL Studio.

Теперь `File.Metadata()` извлекает версию, название, артиста, темп и длительность без поиска зависимостей. Список проектов, метаданные трека и проверка версии используют этот путь; `Analyze` продолжает получать полный список сэмплов и плагинов. Публичные поля API и правила выбора FLP не менялись.

Кэш различает частичный и полный результат. Запрос полного анализа дополняет частичный результат; последующие запросы метаданных не могут заменить полный результат частичным, включая одновременное выполнение. Размер и время изменения FLP по-прежнему проверяются при каждом обращении. Ошибки разбора тоже кэшируются и сбрасываются после изменения файла.

Файл кэша изменён с `flp-index-v4.json` на `flp-index-v5.json`. Это позволяет ранней версии приложения продолжать читать свой прежний кэш, не принимая частичные данные за полный поиск зависимостей. При первом запуске нового кода индекс v5 заполняется заново; настройки аккаунта и проектов не мигрируют и не меняются.

## Измерения API

Windows/amd64, i7-11800H, Go 1.22.12, три повтора по `500ms`, медианы. Запросы проходят настоящий HTTP handler, проверку заголовка, сериализацию JSON и прикладную логику через `httptest`, без TCP и браузера. Для списка — 20 временных папок, по одному сгенерированному FLP с 1 МиБ состояния плагина; для экрана — одна такая папка. Git-репозиториев и сетевого сервера в этих замерах нет.

`Cold` означает очистку FLP-кэша перед запросом, а не холодный файловый кэш ОС, запуск Windows или приложения. Проверка инструментов Git/LFS предварительно прогрета. `Warm` означает повторный запрос при заполненном FLP-кэше. Время очистки кэша входит в оба сравниваемых варианта. На другой системе результаты могут отличаться; три повтора не являются статистическим доказательством для всех проектов.

| Запрос | До | После | Результат |
|---|---:|---:|---:|
| Быстрый первый список, `/api/state?quick=1`, 20 проектов | 6,81 мс | 6,72 мс | практически без изменений |
| Список с метаданными, холодный FLP-кэш | 128,54 мс | 29,40 мс | около 4,4× быстрее |
| Список с метаданными, прогретый FLP-кэш | 20,38 мс | 21,07 мс | сопоставимо; ускорение не подтверждено |
| Данные экрана проекта, `/api/project`, холодный FLP-кэш | 6,87 мс | 1,92 мс | около 3,6× быстрее |
| Данные экрана проекта, прогретый FLP-кэш | 1,90 мс | 1,30 мс | около 1,5× быстрее |

При повторном запросе экрана суммарные выделения сократились примерно с 1,05 МиБ до 23 КиБ: большой FLP больше не читается повторно только ради версии. Это `B/op`, не пиковая память приложения. Список с холодным кэшем всё ещё читает сами FLP: оптимизация пропускает поиск внутри состояний, а не дисковое чтение.

Нельзя называть эти числа временем до появления первого кадра, реакцией на клик или ускорением всего приложения. Не измерялись WebView/GPU, рендеринг DOM, загрузка настоящих библиотек плагинов, Git-репозитории с большой историей, сетевые запросы и холодный диск.

## Корректность и проверки

Проверяются артист, название, темп и длительность в ответах, переход от списка к полному анализу с сохранением сэмплов и плагинов, восстановление частичного кэша с диска, обновление после изменения/повреждения FLP и конкурентные запросы полного и частичного анализа. Полный анализ остаётся отдельной работой: список не возвращает неполные данные вместо списка зависимостей.

Локально прошли новые тесты API/кэша, выбранные Windows-тесты приложения, тесты FLP/UI, `go vet`, проверки JavaScript и сборка Windows. Отдельный запуск существующего `TestScanCaches` на Windows завершился ошибкой: его фикстура ожидает обнаружение плагина в `~/.vst3`, то есть предполагает Linux-пути. Этот тест не менялся; он входит в полный Linux CI. Новые проверки кэша работают на обеих платформах. В Linux и Windows CI добавлен короткий запуск бенчмарков API, Windows CI включает новые функциональные тесты.

Все проекты и аккаунт интерфейса синтетические. `TestMain` изолирует HOME, USERPROFILE, APPDATA, LOCALAPPDATA и XDG_CONFIG_HOME. Фикстура устанавливает пустой список плагинов и пустой индекс библиотек сэмплов, чтобы случайные байты состояния не запускали поиск в системных библиотеках.

## Визуальная проверка: ограничение

Создан опциональный `TestUIFixture`: настоящий интерфейс из `web.FS`, loopback-сервер на случайном порту и 20 синтетических проектов. Он не запускает poller, обновление, LAN discovery и другие фоновые циклы установленного приложения. Каталог доступных серверных проектов подменён пустым результатом. Фикстура по умолчанию пропускается; включается только через `FRUITYHUB_UI_FIXTURE=1`.

Сервер вне песочницы ответил HTTP 200. Встроенный браузер не смог подключиться к Windows loopback. При попытке проверки в локальном Edge инструмент computer-use остановил управление: не удалось достаточно надёжно определить текущий URL браузера для применения политики. После этого UI-автоматизация не продолжалась; тестовый сервер остановлен, временные данные очищены `TestMain`.

Следовательно, успешное отображение списка и экрана проекта **визуально не подтверждено**, задержка от клика до отрисовки не измерена. Это оставшаяся часть третьего этапа перед решением о выпуске 0.10.0; её нужно проверить в доступной изолированной сессии браузера/WebView.

## Повторение

`./scripts/benchmark.ps1 -Go ./dist/bench/tools/go/bin/go.exe -Bench '^BenchmarkUILatency$' -Benchtime 500ms -Count 3 -OutputDirectory dist/bench/stage3-after`

Исходные серии — `dist/bench/stage3-before/app.txt` и `dist/bench/stage3-after/app.txt`, параметры — соседние `environment.txt`. Эти артефакты остаются локальными и не включаются в Git. Для опциональной визуальной фикстуры запустить `go test ./internal/app -run '^TestUIFixture$' -v -count 1` с `FRUITYHUB_UI_FIXTURE=1`, открыть выведенный URL и завершить через `/api/quit` с тестовым заголовком `X-FLSync: fixture-token`. Временная сессия ограничена восемью минутами; рабочая установленная программа для этого не используется.
